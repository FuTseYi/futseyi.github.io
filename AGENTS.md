# FuTseYi website — AI maintenance rules

The goal is a **small, durable, professional academic homepage**. Avoid adding a framework or complex infrastructure.

- Public identity: **FuTseYi / Shine**. Do not use FuXieyi or copy other researchers' credentials.
- Homepage: `index.html` (semantic HTML). All homepage-local assets use relative paths so the file can be opened directly on Windows/macOS. The homepage Blog links point to the live blog because it is generated by CI. Small progressive-enhancement navigation script: `assets/site.js`.
- CSS: `assets/style.css`, shared by the homepage and Blog.
- Articles: `posts/*.md`, with title, date, description and optional comma-separated tags; optional `draft: true`.
- Publish: `.github/scripts/build.py` (Python-Markdown), `.github/workflows/deploy.yml` (GitHub Pages).
- Generated HTML: `blog/` is ignored and regenerated from `posts/` during deployment; never commit generated HTML.
- Keep the design understated, readable, accessible, and responsive. The header uses a sticky navigation and accessible mobile menu; on the homepage a wide-screen directory tracks section state. Preserve keyboard Escape handling, `aria-expanded`, `aria-current`, and no-JavaScript fallback.
- NEVER publish private contact details, unsupported achievements, or inferred publications/jobs. Use only the public email: hello@futseyi.com.
- **Important GitHub writes:** when creating a Git tree via the API, ALWAYS specify the current commit's `base_tree_sha`. Without it, unrelated files/directories may disappear. Verify the full tree after updating the branch.
- Homepage-only preview: open `index.html` directly, without Python or a local HTTP server. For full Blog/build changes, reproduce CI: install `Markdown>=3.7,<4`, run `python .github/scripts/build.py`, stage the output as the workflow does, and run `python .github/scripts/verify.py`. The generator validates post metadata before replacing old generated files; a clean rebuild removes pages for deleted posts. Broken local images/links should fail verification.
- Cross-platform full local preview: use `preview.py` with Python 3.10+ (see `PREVIEW.md`). It builds and verifies `_site/`, converts production navigation links only in the preview copy, and serves on loopback. Re-run after edits; production source links stay unchanged.
- When adding a post, edit `posts/*.md`; the build will regenerate `blog/index.html` and article pages automatically.
- Do not migrate old `My-Website` content without reviewing privacy, image paths and URL preservation.

- Homepage Blog section links to the blog index intentionally; do not hardcode the latest article in the homepage.
- Images for Markdown articles belong in `assets/images/` with root-absolute paths. Keep alt text and use optimized image files.

- Profile README: `.github/scripts/sync_readme.py` derives `README.md` from the homepage hero (name, `.bio`, `.profile-note`, `.profile-languages`, `.profile-motto`, mailto/`.profile-website` URL) and non-draft `posts/*.md`. Personal details and mottos belong in `index.html`, never duplicated as hardcoded text in the generator. The site deploy injects a matching Latest Posts list into the published homepage; the source HTML stays directly previewable. The two repository READMEs must be byte-for-byte identical; never manually edit a generated README. GitHub Actions pushes a changed README locally; remote updates require `PROFILE_README_TOKEN` secret scoped only to `FuTseYi/FuTseYi` Contents write.

- Active In is manually curated in `index.html`; only include user-confirmed organizations and roles. Do not infer job titles or formal affiliations from GitHub membership.
- Recent Open Source Contributions is generated by `.github/scripts/sync_activity.py` into `_site/index.html`. After the normal Blog build/staging and README homepage injection, run `python .github/scripts/sync_activity.py --refresh` to query public activity, then run `verify.py`. Offline behavior is tested with `python -m unittest discover -s .github/scripts -p test_sync_activity.py -v`.
- The existing Publish website workflow refreshes contributions on manual dispatch and monthly on day 1 at 01:17 UTC (09:17 Asia/Shanghai). Ordinary pushes deploy the site using the previous snapshot, without querying fresh GitHub activity. No additional personal token is required: Actions uses its read-only `GITHUB_TOKEN` for public metadata.
- Public activity is limited to the API's recent window (currently 30 days / 300 events). Select the user's branch pushes and authored non-draft PR events, deduplicate repositories by latest activity, and retain up to twelve public, non-archived repositories, showing three initially with an accessible expand/collapse control. Stars, watches, other actors and private repositories are excluded. This is an activity summary, not a complete contribution history.
- `_site/contributions.json` stores only the displayed public metadata and refresh timestamp. Ordinary builds reuse it locally or retrieve the previously deployed JSON; if refresh fails, retain the previous snapshot or the source GitHub-activity link. Do not commit generated snapshots, mock articles, or `_site/` content. Direct-file preview shows the static activity link; full local preview requires the staged build.
